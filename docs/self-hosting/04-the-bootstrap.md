# 4. The bootstrap

*Code: `src/boot.rs`, `examples/bootstrap.rs`. The result: `boot/compiler.image`. Tests:
`tests/bootstrap.rs`.*

## The chicken and the egg

The compiler is an EELisp program. To compile it, you need a compiler. Every self-hosted
language solves this the same way: an older implementation runs the new compiler once, the
compiler compiles itself, and from then on it can carry on by itself.

Our older implementation is the tree-walking interpreter, and it never goes away. It is the
**stage 0** that can always rebuild everything from source.

## Three stages

**Stage 0.** The interpreter loads `src/compiler.eel` and runs it. That compiler then compiles
every top-level form of `src/compiler.eel`, one after another. Printed out, the results are
**image 1**: the compiler, as bytecode, produced by an interpreted compiler.

**Stage 1.** A brand new engine loads image 1, and *only* image 1. It never sees the compiler's
source. Running those protos defines the compiler's functions, so the compiler now exists purely
as bytecode on the VM. That compiler compiles `src/compiler.eel` again: **image 2**.

**The check.** Image 1 and image 2 must be identical, character for character.

Why that check proves something: image 1 was made by the *interpreted* compiler, image 2 by the
*compiled* one. If compiling had changed the compiler's behavior anywhere (a branch taken
differently, a tail call mishandled, a label numbered differently), it would show up as a
different image. Identical images mean the compiled compiler does exactly what the source says.
This is called reaching a **fixed point**: compiling the compiler again changes nothing.

```rust
pub fn stage0() -> Result<String, LispError> {
    let it = Interpreter::new();
    it.eval_all(COMPILER)?;          // the interpreter runs the compiler…
    compile_image(&it, COMPILER)     // …which compiles itself: image 1
}

pub fn stage1(image: &str) -> Result<String, LispError> {
    compile_image(&with_image(image)?, COMPILER)   // bytecode only: image 2
}
```

It reached the fixed point on the first run.

## The image

`boot/compiler.image` is about 50 KB of plain EELisp, one `(proto …)` per top-level form of the
compiler. It starts like this:

```lisp
;; The EELisp compiler, compiled by itself: one (proto …) per top-level form of
;; src/compiler.eel, in order. Generated by `cargo run --example bootstrap`; don't edit by hand.
(proto :name nil :params () :source ((def compiler-fallbacks 0)) :code ((const 0) (def compiler-fallbacks)))
(proto :name nil :params () :source ((def compiler-label-n 0)) :code ((const 0) (def compiler-label-n)))
…
```

Because bytecode is EELisp data, the image is readable, diffable in a pull request, and read
back by the same reader that reads source code. It contains 36 protos and no `(interp …)` at
all: every part of the compiler is compiled.

## Keeping the image true

Committing a generated file invites it to go stale, so the tests watch it:

- `the_committed_image_is_what_the_compiler_makes_of_itself` runs stage 0 and compares it with
  the committed file. Change `compiler.eel` without regenerating, and this test fails with the
  command to run.
- `the_compiled_compiler_compiles_itself_to_the_same_image` runs stage 1 from the committed
  image and requires the fixed point.
- `an_image_reads_back_as_itself` parses the image and prints it again, line by line.
- `an_engine_started_from_the_image_compiles_and_runs_programs` boots an engine from the image
  alone and compiles a factorial, a macro and a `for-each` with it.

The differential test from the previous chapter also runs a fourth time with the compiler loaded
from the image, and all 471 snippets still agree.

To regenerate the image:

```
cargo run --example bootstrap
```

It runs both stages and refuses to write the file if they disagree.

## How fast is it?

Not faster yet, and we expected that. In a release build, stage 0 (interpreted compiler) and
stage 1 (compiled compiler) both take about 17 ms. Compiled code still looks up every variable by
name in the same environments the interpreter uses, so the main cost hasn't gone anywhere. What
has gone is re-deciding what each form is on every run. Resolving local variables to numbered
slots is where the speed will come from, and the tests now make that change safe to attempt.

## Where this leaves us

EELisp now has a compiler written in EELisp that compiles itself to a fixed point. The engine
still evaluates with the interpreter by default; switching `eval` to compile-and-run is the next
step, once a benchmark built from real editor workloads says it's ready.
